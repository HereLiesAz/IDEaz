## Production Readiness
- Fixed a gated on-device model's 403 download failure telling the user to "visit its page on huggingface.co and accept the license" with no way to actually get there — the Settings screen showed that sentence as plain error text, same as any other failure message. Added `ModelDownloadManager.huggingFaceRepoPageUrl()`, which derives a model's Hugging Face repo page (e.g. `https://huggingface.co/litert-community/Gemma2-2B-IT`) from its `resolve/<revision>/<path>` download URL, and `OnDeviceModelsSection` now renders it as a tappable "Open on Hugging Face to accept the license ↗" link right under the error whenever a download fails with HTTP 403 — the same clickable-link pattern the card already uses for `licenseUrl`. `licenseUrl` itself (Gemma's general terms page) was the wrong target for this: the 403 gate lives on the specific gated repo, not Google's terms page.
- `build-and-release.yml`'s "Merged Build & Release" run for PR #853 (the Jackson 2.18.10 bump) failed at `:app:packageRelease` with the same opaque, stack-trace-free `PackageAndroidArtifact$IncrementalSplitterRunnable` error that killed the two earlier Jackson-bump attempts (see the entry above) — the third time this exact failure has coincided with a Jackson-family dependency bump, always in this one workflow, never locally (validated with `--stacktrace` before merging) and never in `pr-check.yml`'s `check` job (which never runs `packageRelease` at all). Leading theory: `setup-gradle`'s GitHub-Actions-backed cache persists Gradle's own local task-output build cache (not just downloaded dependency jars) across runs, and a dependency bump touching this many jars at once is a plausible way for a stale cached task output to escape its own cache-key invalidation and feed inconsistent input into packaging. Fixed by dropping `--build-cache` from this workflow's default Gradle invocation (dependency-jar caching is untouched, still fast) and always appending `--stacktrace` regardless of where `BUILD_COMMAND` came from, so any recurrence is actually diagnosable instead of a third round of guessing. Not yet confirmed as the real root cause — the next `build-and-release.yml` run is the test.
- Fixed the on-device wasm-preview reload path's whole-cache nuke: every wasm-compile-success reload called `webView.clearCache(true)` to work around `WebProjectPathHandler`'s responses never declaring cache freshness, discarding everything else cached (fonts, unrelated assets) along with it. `WebProjectPathHandler` now marks project content `Cache-Control: no-store` (correctness needs no whole-cache wipe), while the bundled `/__ideaz__/` runtime (~4.5MB, static per app version) stays cacheable and is now versioned into its own URL path (`RUNTIME_PREFIX` includes `BuildConfig.VERSION_CODE`) so an app upgrade can't leave stale cached runtime JS served under an unchanged URL. Also restored explicit root navigation (`loadUrl(localProjectRootUrl())`) on wasm-compile-success instead of a plain `reload()` — a Compose Multiplatform app can push its own History API entries, so the WebView may not be sitting at the freshly-mounted output's root — and re-added the `Ideaz`/`IdeazBridge` JS interfaces at that same navigation point, since they'd otherwise stay stripped if the page had last navigated away from this app's own origin. This does not make the reload state-preserving: Kotlin/Wasm has no JVM-style live class redefinition to build that on top of.

- Fixed `build-and-release.yml` and `publish-play.yml` deriving `BUILD_NUMBER` from the `build` field in `version.properties` — a value nothing in either pipeline ever increments or commits back, so every CI build and every Play Store upload attempt baked in the exact same versionCode/versionName no matter how many commits had actually happened since the field was last hand-edited. Both now compute `BUILD_NUMBER` from `git rev-list --count HEAD` instead, a value that only ever grows with real repository history, matching the `-PversionBuild=$BUILD_NUMBER` convention `app/build.gradle.kts` already expected CI to supply.
- Split `build-and-release.yml`'s release publishing into two independent tracks so an ordinary push to `master` can no longer silently overwrite a deliberately-cut release: every push now force-tags `debug-v$major.$minor` and publishes/updates a prerelease ("Latest Debug Build"), while the real "Latest Release" (`v$major.$minor`, not marked prerelease) only ever publishes on a manual `workflow_dispatch` run. Previously a single tag/release covered both cases, so any routine push retargeted whatever release someone had last intentionally promoted.
- Bumped the pinned Jackson dependency family (`app/build.gradle.kts`'s dependency-resolution `eachDependency` block) to 2.18.10, closing all 9 open Dependabot alerts (CVE-2026-54512, -54514, -54515, -59889, and siblings — PolymorphicTypeValidator bypasses, an `InetSocketAddress` SSRF, a case-insensitive-deserialization `@JsonIgnoreProperties` bypass, a `@JsonView`/`@JsonUnwrapped` bypass, and jackson-core's async-parser `maxNumberLength` bypass). Two earlier attempts (documented previously in this entry and in the resolution-strategy comment) had reverted the same move: a simultaneous Netty bump hanging CI's `Build with Gradle` with zero diagnostics, then an opaque, stack-trace-free `:app:packageDebug` failure the CI log gave no way to diagnose. This attempt used this environment's now-working local Android SDK to reproduce and diagnose locally instead of guessing blind against CI: `:app:packageDebug --stacktrace`, `:app:checkDebugDuplicateClasses`, and a full `./gradlew build` all pass clean at 2.18.10, and `:app:dependencies --configuration debugRuntimeClasspath` confirms every Jackson module resolves to 2.18.10 tree-wide with no conflicts. The prior failure never reproduced — whatever caused it looks CI-runner-specific rather than a real Jackson incompatibility.
- Root-caused why every credential save was failing on real devices, invisible to this repo's own unit tests: `AndroidKeystoreCredentialStore.encryptCredential()` passed a caller-generated IV into `Cipher.init(ENCRYPT_MODE, key, GCMParameterSpec(...))`, which an AndroidKeyStore-backed key built with `setRandomizedEncryptionRequired(true)` (the default, and what this store sets explicitly) rejects outright with `InvalidAlgorithmParameterException: Caller-provided IV not permitted` on every call, on every device — the file's own unit test never caught this because it exercises a plain software AES key with no such restriction. Fixed by initializing without an IV and reading the provider-generated one back via `cipher.iv`, the standard required pattern for AndroidKeyStore-backed GCM encryption. Separately, `SettingsViewModel.saveString()` had its own decoupling bug that had been silently reporting every one of those failures (and any future ones) as success: it conflated the real secure-credential write with an unrelated best-effort legacy-plaintext-cleanup step, so a cleanup hiccup — or, before the Keystore fix above, literally every save — never surfaced to the UI. Fixed by tracking the two operations' success independently. GitHub-token save now also triggers `fetchGitHubRepos()` so the Clone tab refreshes immediately instead of requiring a manual retry after saving a token, and default AI model selection now ranks by which provider keys are actually saved (`AiModels.defaultRanking`, resolved through `SettingsViewModel`'s `defaultModelId()`) instead of hardcoding Gemini as the fresh-install fallback.
- Added an "Open App Info" button to Settings → Permissions (`SettingsScreen.kt`, launches `Settings.ACTION_APPLICATION_DETAILS_SETTINGS`) so users can reach the system App Info screen directly — the one path off Android's "restricted settings" block on sideloaded apps, which otherwise silently disables permission toggles with no in-app guidance for how to unblock them.
- Fixed `OperationControllerTest.kt`: 7 of its 12 tests failed in CI — merged to master anyway (`pr-check.yml`'s `check` job was red on that commit). Root cause: `@Before` built `OperationController(testScope.backgroundScope)` once and reused it across every `@Test`, but `TestScope.backgroundScope` accessed outside an active `runTest` call doesn't reliably share the scheduler that `advanceUntilIdle()`/`runCurrent()` inside that later `runTest` block actually drives — coroutines the controller launched weren't being advanced by the test's own scheduler calls, so assertions checking a post-`advanceUntilIdle()` terminal state (Succeeded/Failed) saw stale state instead. Fixed by constructing a fresh `OperationController` inside each test from the `runTest` lambda's own `TestScope` receiver (`OperationController(this)`) — the standard, unambiguous pattern for testing anything coupled to a `CoroutineScope` under `kotlinx-coroutines-test`.
- Started P0.5 (unify long-running operation state — clone, create/init, AI, build, deploy, download, update, Git). Researched actual current state first rather than guessing: none of the eight categories share any state type today (confirmed via a full-tree grep for `TaskState`/`OperationState`/`LoadingState`/`AsyncResult`-shaped types — zero hits beyond two narrow, unrelated ones). Six of the eight have no cancel and no user-facing retry at all; only the on-device model downloader (`LocalModelDownloadWorker`, WorkManager-backed) has real progress, cancel, retry, and process-death survival — everything else is a bare `Boolean`/`Job?`/log-string mix that resets on process death. A single PR unifying all eight isn't feasible or wise: they sit on genuinely different substrates (WorkManager is correct for downloads and would be the wrong tool forced onto an interactive Git call; AI chat is conversational, not a discrete job). Shipped the first, foundational increment only: `models/OperationState.kt` (a `sealed interface OperationState<T>` — Queued/Running(progress)/Succeeded/Failed(retryable)/Cancelled — plus `OperationProgress` and `isRetryable()`/`isTerminal()` helpers) and `utils/OperationController.kt` (runs one operation at a time on a given `CoroutineScope`, publishes lifecycle to a `StateFlow`, supports `start`/`cancel`/`retry`, and a `NonRetryableOperationException` a block can throw to mark its own failure as not worth retrying). Neither is wired into any existing delegate yet — this PR is deliberately just the shared primitive, unit-tested in isolation (`OperationStateTest.kt`, `OperationControllerTest.kt`), so it can prove itself before delegates migrate onto it. Writing the tests caught a real bug before it shipped: `isActive` originally treated the controller's idle/never-started `Queued` default as "busy," which would have made `start()` silently refuse to ever run on a fresh controller — fixed to check only `Running`, with a regression test locking in the fix. **Deliberately deferred, matching the pattern this session used for AI-edit-approval's 3-provider rollout:** migrating Build and Git (the two best-scoped candidates — each already tracks a `Job`/progress callback that just needs swapping for the new `StateFlow<OperationState>`) is next; Clone/Create-Init and Update after that, adding real user-triggered retry where none exists today; AI chat and the on-device downloader last (downloader should mostly stay on WorkManager, just optionally exposed through the same shape at the UI boundary).

- Root-caused and fixed the `build-and-release.yml` `Build with Gradle` hang (previously mitigated only with `timeout --kill-after=1m 30m` + live `tee` streaming + a JVM thread-dump watchdog, since neither the Netty/Jackson version bump nor Gradle's Enhanced Caching provider turned out to be the cause). A `jcmd Thread.print` captured mid-hang showed `:app:testDebugUnitTest`'s executor thread permanently blocked in `AsyncDispatch.stop() -> waitForAllMessages()` during Gradle's own test-executor teardown — every task after it in the graph (including the entire `:webruntime` module) completed normally in parallel, but the whole build can't finish until every task action's thread returns, including this stuck one. Root cause: `AIDelegateTest.kt`'s `@Before setUp()` and `pullRequestEventForwardsUrlToCallback()` each built a real `CoroutineScope(Dispatchers.Unconfined)` and wired it into a real `AIDelegate` (Robolectric, not `@Ignore`'d, runs every build) without ever cancelling it — unlike the sibling `SystemEventDelegateTest.kt`, which calls `cleanup()` on the same delegate constellation but is itself `@Ignore`'d. Since `app/build.gradle.kts` sets no `forkEvery`, the whole module's unit tests run in one forked JVM, so this single leaked scope was enough to hang the entire task's shutdown. Fixed by capturing the scope as a field and cancelling it in `@After`. `SystemEventDelegateTest` and `CrashReportingServiceTest` remain `@Ignore`'d with a "Crashes Robolectric runner in CI environment" note from a prior incident — worth re-investigating in isolation now that this shape of bug is understood. `OverlayDelegateWebContextTest`'s 3 flaky failures are unrelated (plain Mockito, no Robolectric, no owned threads) — likely `runTest`/`TestScope` timing sensitivity around its `delay(250)` path, not a teardown hang; still needs its own investigation.
